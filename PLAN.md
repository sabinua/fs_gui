# FreeSWITCH GUI — початковий план

Мультиплатформенний десктоп-додаток для керування FreeSWITCH через ESL (Event Socket Library) з підтримкою підключення через SSH-тунель.

Ключові вимоги ядра:
- **Менеджер підключень**: додавання/редагування/видалення профілів, зберігання секретів у keychain.
- **Декілька одночасних підключень**: кожен сервер — окрема вкладка зі своїм повним дашбордом.
- **Плагінна архітектура**: функціональні модулі (Call Center першим) — окремі плагіни поверх стабільного Core API.

## 1. Рекомендований стек технологій

### Основний варіант: Wails v2 (Go) + React + TypeScript

| Шар | Технологія | Обґрунтування |
|---|---|---|
| Оболонка | **Wails v2** | Легкі бінарники (~10 МБ проти ~150 МБ Electron), нативне вікно, Windows/Linux/macOS |
| Backend | **Go** | Відмінна робота з мережею та конкурентністю — ідеально для стрімінгу подій ESL |
| ESL-клієнт | `percipia/eventsocket` або власна реалізація протоколу (він простий: текстовий, ~10 команд) | Прямий контроль над inbound-з'єднанням |
| SSH | `golang.org/x/crypto/ssh` | Нативний SSH-тунель без зовнішніх залежностей, підтримка ключів/agent |
| Frontend | **React 18 + TypeScript + Vite** | Швидка розробка, велика екосистема |
| UI-кіт | **shadcn/ui + Tailwind CSS** | Сучасний вигляд, темна/світла тема з коробки |
| Стан | **Zustand** + події Wails (runtime events) | Простий стор, push-оновлення з backend |
| Локальна БД | **SQLite** (`modernc.org/sqlite`, без CGO) | Кеш CDR, історія подій, профілі підключень |
| Графіки | **Recharts** | Дашборд: дзвінки/час, навантаження |

### Альтернатива: Electron + Node.js
`modesl` (ESL) + `ssh2` (тунель) + React. Швидший старт, більше прикладів, але важчі бінарники та більше споживання RAM. Обирати, якщо команда суто JS/TS.

### Чому не Tauri
Tauri (Rust) дає найменші бінарники, але ESL-бібліотеки для Rust незрілі, а поріг входу вищий. Go — золота середина.

## 2. Архітектура

```
┌───────────────────────────────────────────────────────────┐
│  Frontend (React/TS)                                      │
│  ┌─ Менеджер підключень (сайдбар/стартовий екран) ──────┐ │
│  │  профілі: додати / редагувати / видалити / клонувати │ │
│  └──────────────────────────────────────────────────────┘ │
│  ┌─ Вкладки: [ PBX-Kyiv ✓ ][ PBX-Lviv ✓ ][ + ] ─────────┐ │
│  │  усередині вкладки — повний UI одного сервера:       │ │
│  │  Dashboard · Calls · Directory · CDR · Events        │ │
│  │  · Dialplan Tracer · <сторінки плагінів>             │ │
│  └──────────────────────────────────────────────────────┘ │
└──────────────▲────────────────────────────────────────────┘
               │ Wails bindings + runtime events (усі з connId)
┌──────────────┴────────────────────────────────────────────┐
│  Backend (Go)                                             │
│  ┌─ ConnManager ────────────────────────────────────────┐ │
│  │  CRUD профілів (SQLite + keychain)                   │ │
│  │  map[connId] → Session (N одночасних сесій)          │ │
│  └──────┬───────────────────────────────────────────────┘ │
│  ┌──────▼─ Session (на кожне активне підключення) ──────┐ │
│  │  ESL Client ──(TCP напряму або SSH local forward)    │ │
│  │  EventBus: підписки, фільтри, роутинг у frontend     │ │
│  │  екземпляри Core-модулів і плагінів                  │ │
│  └──────────────────────────────────────────────────────┘ │
│  ┌─ Core-модулі ───────────┐  ┌─ Plugin Host ──────────┐  │
│  │ Calls · CDR · Directory │  │ реєстр, lifecycle,     │  │
│  │ Events · DialplanTracer │  │ Core API для плагінів  │  │
│  └─────────────────────────┘  │ → CallCenter (перший)  │  │
│  ┌─ SQLite ────────────────┐  └────────────────────────┘  │
│  │ профілі · CDR · події   │                              │
│  │ (шардовано за connId)   │                              │
│  └─────────────────────────┘                              │
└───────────────────────────────────────────────────────────┘
```

Ключові принципи:
- **Session-модель**: кожне активне підключення — ізольована сесія (свій ESL-клієнт, свій EventBus, свої екземпляри модулів). Усі виклики bindings та всі push-події несуть `connId` — frontend роутить їх у відповідну вкладку. Падіння/reconnect однієї сесії не зачіпає інші.
- **Одне ESL-з'єднання на сесію** з автоматичним reconnect та чергою команд; події та `api`-команди мультиплексуються.
- **SSH-тунель** — опційний шар: backend піднімає local port forward до `127.0.0.1:8021` на сервері, ESL підключається до локального кінця. Автентифікація: пароль / приватний ключ / ssh-agent.
- **Push-модель**: backend підписується на події один раз, фільтрує та штовхає у frontend через Wails events — без polling.
- Паролі ESL/SSH — у системному keychain (`zalando/go-keyring`), не у відкритих конфігах.

### Менеджер підключень

- Профіль: назва, host/port ESL, пароль ESL, транспорт (напряму / SSH), параметри SSH (host, port, user, пароль/ключ/agent), колір/іконка вкладки, автопідключення при старті, теги.
- Дії: додати, редагувати, видалити (з підтвердженням), клонувати, тест з'єднання прямо з форми (перевірка SSH і ESL окремо, зі зрозумілими помилками).
- Метадані профілів — у SQLite, секрети — тільки в keychain; експорт/імпорт профілів без секретів (JSON).
- Стартовий екран — список профілів зі статусами; підключення відкриває вкладку. Індикатор стану на самій вкладці (🟢 online / 🟡 reconnect / 🔴 offline).

### Плагінна архітектура

Два рівні, щоб не переускладнити v1:

**v1 — вбудовані плагіни (compile-time registry).** Плагін — Go-пакет, що реалізує інтерфейс і реєструється в Plugin Host. Це відпрацьовує сам API, але без проблем динамічного завантаження в Go:

```go
type Plugin interface {
    Manifest() Manifest            // id, назва, версія, залежності від модулів FS
    Init(ctx PluginContext) error  // доступ до Core API
    Shutdown() error
}
// PluginContext (Core API): API(cmd), BgAPI(cmd), Subscribe(events, handler),
// Store(namespace) — своя таблиця в SQLite, EmitUI(event, payload)
```

- Плагін оголошує залежності від модулів FS (напр. `mod_callcenter`) — Plugin Host перевіряє через `module_exists` при відкритті сесії та вмикає/вимикає плагін per-connection.
- Frontend-частина плагіна реєструє свої сторінки/віджети через contribution points: пункт бокового меню вкладки, картки на дашборді, розділ у налаштуваннях.
- Плагіни вмикаються/вимикаються користувачем per-profile.
- **Call Center — перший плагін**: доводить API до робочого стану на реальному споживачі.

**v2 — зовнішні плагіни.** Backend: окремі процеси через `hashicorp/go-plugin` (gRPC) — без обмежень Go `plugin`-пакета, працює на всіх ОС. Frontend: динамічні ES-модулі з manifest.json. Дизайн Core API у v1 робимо так, щоб він 1:1 мапився на gRPC.

## 3. Функціонал → команди ESL

| Функція | Реалізація |
|---|---|
| Статус сервера | `api status`, `api show modules`, `api sofia status`, uptime, sessions/sec |
| Активні дзвінки | `api show channels as json` + live-оновлення з подій `CHANNEL_CREATE/ANSWER/HANGUP` |
| Розірвати дзвінок | `api uuid_kill <uuid> [cause]` |
| Трансфер | `api uuid_transfer <uuid> [-bleg/-both] <dest> [dialplan] [context]` |
| Змінні дзвінка | перегляд: `api uuid_dump <uuid> json`; редагування: `api uuid_setvar <uuid> <var> <val>` |
| Запис дзвінка | `api uuid_record <uuid> start/stop <path>` + індикатор з подій `RECORD_START/STOP` |
| Директорія | `api list_users` (домени, групи, статус реєстрації) + `api show registrations` |
| Call Center | `api callcenter_config queue list / agent list / tier list`, `agent add/del`, `agent set status/state/contact`, `tier add/del/set`; live через `CUSTOM callcenter::info` |
| CDR | підписка на `CHANNEL_HANGUP_COMPLETE` (містить усі змінні дзвінка) → запис у SQLite → таблиця з фільтрами/пошуком/експортом CSV |
| Монітор подій | `event json ALL` (або вибрані), фільтри за типом/полями, пауза, live-стрічка |
| Ловля дзвінка + діалплан | фільтр за `destination_number`: ловимо `CHANNEL_CREATE`, далі збираємо `CHANNEL_EXECUTE` / `CHANNEL_EXECUTE_COMPLETE` по UUID — відновлюємо повний ланцюжок виконаних додатків діалплану (app + args + результат), експорт у XML-заготовку extension |

## 4. Етапи розробки

> **Статус (2026-08-05):** етапи 0–6 виконані (каркас, підключення+мультисесії, дашборд+дзвінки, CDR+події, директорія, Plugin Host + Call Center, Dialplan Tracer). Залишився етап 7 — поліровка (i18n, збірки під Win/macOS, автооновлення) та беклог: SFTP-доставка записів, зовнішні плагіни v2.

### Етап 0 — Каркас (~3 дні)
- Ініціалізація Wails-проєкту, React + TS + Tailwind + shadcn/ui, лінтери, CI.
- Структура Go-пакетів: `esl/`, `sshtunnel/`, `store/`, `modules/`.

### Етап 1 — Підключення та мультисесійність (~1.5 тижня)
- ESL inbound-клієнт: auth, `api`/`bgapi`, підписка на події, парсинг JSON-подій, heartbeat, reconnect.
- SSH-тунель (пароль/ключ/agent, known_hosts).
- Session-модель: ConnManager з N одночасними сесіями, роутинг подій за `connId`.
- Менеджер підключень: CRUD профілів, keychain, тест з'єднання, стартовий екран, вкладки з індикаторами стану.
- **Результат:** одночасне стабільне підключення до кількох FS, кожен у своїй вкладці.

### Етап 2 — Дашборд + дзвінки (~1–1.5 тижня)
- Дашборд (у межах вкладки): статус, uptime, sessions, кількість дзвінків, статус sofia-профілів, список модулів, міні-графіки.
- Live-таблиця дзвінків (з подій), картка дзвінка.
- Дії: hangup, transfer (діалог з вибором напрямку), перегляд/редагування змінних, старт/стоп запису.
- **Результат:** MVP — можна показувати.

### Етап 3 — Події + CDR (~1 тиждень)
- Стрічка подій з фільтрами, перегляд сирого JSON, пауза/буфер.
- CDR: збір з моменту підключення у SQLite, таблиця з фільтрами (номер, напрямок, дата, hangup cause), деталі, експорт CSV.

### Етап 4 — Директорія (~3–4 дні)
- Список користувачів по доменах/групах, статус реєстрації, деталі (contact, user-agent, expires).
- Дії: `flush_inbound_reg` тощо.

### Етап 5 — Plugin Host + Call Center як перший плагін (~2 тижні)
- Plugin Host: інтерфейс плагіна, PluginContext (Core API), перевірка залежностей від модулів FS per-connection, contribution points у frontend, вмикання/вимикання per-profile.
- Плагін Call Center:
  - Черги: список, склад, дзвінки що чекають, статистика.
  - Агенти: CRUD, зміна status (Available/On Break/Logged Out) та state, tiers (прив'язка до черг, level/position).
  - Live-борд черги з подій `callcenter::info` (agent-status-change, member-queue-start/end...).
- **Результат:** робочий плагінний API, доведений на реальному модулі.

### Етап 6 — Dialplan Tracer (~1 тиждень)
- Ввід номера → arm фільтра → дзвінок → таймлайн виконання діалплану (крок за кроком, час, змінні на кожному кроці).
- Експорт трасування у XML-extension-заготовку.

### Етап 7 — Поліровка (~1 тиждень)
- Теми, i18n (uk/en), гарячі клавіші, збірки Win/Linux/macOS (GitHub Actions), автооновлення, логування, обробка помилок.

**Разом: ~8–9 тижнів до повнофункціональної v1.0.** MVP (етапи 0–2, вже з мультипідключенням) — ~3 тижні.

У v2: зовнішні плагіни (go-plugin/gRPC + динамічні ES-модулі), SFTP-доставка записів, редагування XML-конфігів через SFTP.

## 5. Ризики та нотатки

- **ESL «all events» на навантаженому сервері** — великий трафік. Підписуватися лише на потрібні типи, «ALL» — тільки у моніторі подій за явним увімкненням.
- **Редагування змінних** діє тільки на активний канал і не змінює конфігурацію FS — чесно відобразити це в UI.
- **Запис** пише файл на сервері FS; для прослуховування з GUI знадобиться доставка файлу (SFTP через той самий SSH — додати в бэклог).
- **callcenter_config** вимагає `mod_callcenter` + його ODBC/sqlite БД на боці FS — перевіряти наявність модуля і gracefully деградувати.
- Редагування XML-директорії/діалплану напряму через ESL неможливе — тільки через файли (SFTP) або mod_xml_curl. У v1 — read-only + tracer, редагування файлів — v2.
